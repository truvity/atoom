# The S3 driver

How the blob contract ([the blob port](../../docs/blob-port.md)) maps to S3. The driver is a Go library; the thin main (`cmd/s3`) only serves it on a socket.

| Call | S3 |
| --- | --- |
| `Create` | `PutObject` at `<prefix><path>` with `If-None-Match: *`. S3's `412 Precondition Failed` (or `409 ConditionalRequestConflict`, a conditional write that raced another) is `already_exists` / `taken`. The answer's tag is the SHA-384 of the bytes written |
| `Put` | refused with `permission_denied` / `rule` before any call when the last segment of the path is not a declared pointer. With an empty `if_match`: `PutObject` with `If-None-Match: *`, and a `412` is `aborted` / `version`. With a tag: `GetObject` of the pointer; absent, or the SHA-384 of its bytes is not `if_match`, is `aborted` / `version`; else `PutObject` with `If-Match` set to the S3 ETag that `GetObject` answered, and a `412`, a `409` or an absent key is `aborted` / `version` |
| `Get` | `GetObject`; `NoSuchKey` is `not_found` / `absent`. The tag is the SHA-384 of the bytes read |
| `List` | `ListObjectsV2` under `<prefix><prefix of the call>`, `StartAfter` set to the page token (the last path of the page before), as many calls as a page needs; a key under the driver's prefix that is not a path of the contract is skipped |

## The entity tag

The port's tag depends on the bytes only ([the blob port](../../docs/blob-port.md#the-contract)). S3's own ETag is the MD5 of the bytes only for an object written in one part without KMS encryption, so the driver does not use it as the port's tag: it computes the SHA-384 of what it writes and of what it reads. It uses S3's ETag in one place, as the condition of the replace of a pointer, where it is exactly what S3 compares.

## Limits

- A path is at most 1024 bytes and a segment 255, as for every blob driver; with the prefix, the key must stay within S3's 1024 bytes, so a host keeps its prefix short.
- One object is at most `Options.ObjectMax` bytes (64 MiB by default) for a write and a read; a larger write is `invalid_argument` / `bound`, field `data`. `PutObject` takes 5 GiB in one part, and the driver makes no multipart upload: a log's tiles and pointers are small.
- A page of `List` is at most 10 000 paths (0 is 1000), as for the `fs` drivers.

## The options a host gives

The bucket, the prefix, the pointer names and the client, with its region, its credentials and its endpoint: the driver knows no region, account or installation ([record 0021](../../../docs/decisions/0021-drivers-know-no-deployment-shapes.md)). The thin main reads the client's configuration from the AWS SDK's chain (the environment, the shared files, the role of the host; `AWS_ENDPOINT_URL_S3` for another endpoint) and takes `--path-style` for a server of S3's protocol that serves its buckets in the path. It sends checksums only where S3 requires them, so that the body goes plain.

## Not tested here

The fake is not S3. The conditional writes of S3 itself, their `409` under contention, the consistency of `ListObjectsV2` after a write, encryption with KMS and bucket policies are the deployment's to check, or a run with `ATOOM_S3_ENDPOINT` against an S3-compatible server that implements both conditional writes. MinIO does, but its images are no longer served from Docker Hub (a pull is refused, checked 2026-11-25), so the conformance run in CI uses the fake.
